# 人生シミュレーション 開発プロセス設計書

> 作成: 2026-06-13
> 目的: 「現実の人生を追体験する、選択が後々に影響する高自由度シミュレーション」をゼロから設計・実装するための工程表。
> 原則: **ロジック設計・デザイン判断・トーン・音の配置は開発者が決める。** AIは分析補助・状態/イベントの検証・モンテカルロ・コンテンツ量産の下書き・実装・調達を担う。
> 関連: 人生ゲーム(すごろく)とは**別ゲーム**として設計する（基盤は共有）。判断の経緯は本書 STEP 0-5 を参照。

## 担当区分の凡例

- 🧑‍🎨 **開発者のみ** — トーン・ゲーム性・面白さの判断。AIに代替不可
- 🤝 **共同** — AIがたたき台/素案を出し、開発者が選定・判断
- 🤖 **AIが確実に担える** — 指示されれば完遂でき品質も保証できる

## このゲームの性質（最初に共有すべき大前提）

1. **本体はエンジンではなくコンテンツ（イベント＝ストーリーレット）の量産**。エンジンは小さい。プロジェクトの工数・品質の9割はコンテンツに乗る
2. **分岐ツリーは作らない**。「ステータス＋フラグ＋条件付きストーリーレット」方式（Fallen London / BitLife / Alter Ego 型）。著作コストはイベント数に線形、体験する組合せは指数的 = 自由度の体感だけを最大化する
3. **状態モデルの設計が全工程の土台**。ここがブレると量産コンテンツが必ず崩壊する（STEP 2 が最重要エンジニアリング）
4. **「人生の不規則性」は条件付き抽選＋隠しパラメータ＋ランダム率ツマミで作る**。サイコロ的な無条件ランダムより良い不規則性が出る（人生ゲームと混ぜない理由）

## 工程全体図

```
STEP 0   コンセプト & 根本分岐の確定（このゲームの魂）
STEP 1   リファレンス分析（BitLife / Alter Ego / Fallen London 他の解剖）
STEP 2   状態モデル設計 ★基盤（stats/flags/relations/resources/隠し値/派生値）
STEP 3   イベント(ストーリーレット)スキーマ設計（宣言的条件DSL）
STEP 4   コアループ & システム設計（抽選・ライフステージ・終了条件・マルチ）
STEP 5   技術基盤の決定（現Webスタック / エンジン）
STEP 5.5 ★垂直スライス — 5シーンで誕生から死まで通す「骨格の一周」
STEP 6   コンテンツ設計 & 量産パイプライン ★本体
STEP 7   画面・UX設計
STEP 8   ビジュアル（CPK 部品キット）
STEP 9   SE・BGM
STEP 10  実装（エンジン → 統合）
STEP 11  検証（モンテカルロ）& プレイテストループ
STEP 12  完成判定・リリース
```

**STEP 2〜4（状態モデル・イベントスキーマ・コアループ）は技術基盤に依存しない。** エンジン選定(STEP 5)前に確定させてよい。

**★ 開発順序の方針（2026-07-27 決定）: 設計を詰め切る → 骨格を小規模に一周させる → 間を埋める。**
設計（STEP 2〜5）を先に固め切ってから、**STEP 5.5 で5シーン程度の「誕生から死まで」を実際に遊べる形で通す**。それを骨組みとして、STEP 6 以降でイベント・エンディング・演出を間に詰めていく。

理由: (1) 500本を量産してから状態モデルの誤りに気づくと全件手直しになる (2) 統合の問題（状態モデル ↔ イベントスキーマ ↔ コアループ ↔ 演出）は各層を個別に作っていても見つからない (3) 「面白いか」はドキュメントからは判定できない。

**ただし「すべてを設計で詰め切る」ことはできない。** 紙の上で決められる問いと、遊んでみないと答えが出ない問いを分ける（STEP 5.5 の「詰め切る／スライスで答える」表を参照）。後者を設計フェーズで無理に決めると、確度の低い決定を根拠にしてしまい、かえって手戻りを生む。

## STEP 2. 状態モデル設計 ★基盤

**成果物**: `data/lifesim/state_schema.json`（状態の正史）＋設計メモ — **判断は🧑‍🎨、スキーマ整備とバリデータは🤖**

> ここがプロジェクトの背骨。これが曖昧だと量産コンテンツが必ずドリフトする（あるイベントは `married` をセット、別のは `flag_married` を参照、のような事故）。

| サブステップ | 内容 | 担当 |
|---|---|---|
| 2-1 | **ステータス定義**: 有界数値(0-100)。何を測るか（例: 知力/体力/魅力/メンタル/健康…）。種類と意味を確定 | 🧑‍🎨 |
| 2-2 | **リソース定義**: 無限大スケール（お金/借金/時間など） | 🧑‍🎨 |
| 2-3 | **フラグ定義 & 名前空間規約**: 真偽の事実（取得資格/職歴/出会い/持病/隠し事）。`edu.* / job.* / rel.* / habit.* / secret.*` の名前空間で増殖を管理 | 🧑‍🎨方針 → 🤖整備 |
| 2-4 | **人間関係モデル**: relations は真偽でなく強度(数値)を持つ。誰を個別エンティティにするか（母/親友/上司…） | 🧑‍🎨 |
| 2-5 | **隠しパラメータ枠**: プレイヤーに見せない値(運/カルマ/死亡リスク…)を最初から区別。「なぜか自分だけ事故る」ドラマの源。後付け困難 | 🧑‍🎨 |
| 2-6 | **派生値の定義**: 「社会的地位」「モテ度」等は保存せず job+money+charm から毎回計算する読み取り専用値（イベントは参照可・セット不可） | 🤝 |
| 2-7 | **履歴(history)の設計**: 同窓会型の回想イベント＆人生ダイジェスト用に、どの選択を記録するか | 🧑‍🎨 → 🤖 |
| 2-8 | state_schema.json のスキーマ化＋ランタイム/ビルド時バリデータ実装 | 🤖 |

**状態ドキュメントの例（種類で名前空間を分ける）:**
```json
{
  "age": 24, "stage": "young_adult",
  "stats":     { "intelligence": 62, "fitness": 40, "charm": 55, "mental": 70, "health": 85 },
  "resources": { "money": 1200000, "debt": 0 },
  "flags":     ["edu.univ_graduated", "job.parttime_xp", "rel.childhood_friend", "habit.smoking"],
  "relations": { "mother": 70, "best_friend_ken": 45, "boss": -10 },
  "hidden":    { "luck": 38, "karma": 5, "health_risk": 0.12 },
  "job":       { "id": "engineer", "years": 2, "salary": 4200000 },
  "history":   [ { "age": 17, "event": "quit_club", "choice": "band_instead" } ]
}
```

**完了条件**: state_schema.json が確定し、バリデータが動く。以降の全イベントはこれに対して検証される。

## STEP 3. イベント(ストーリーレット)スキーマ設計

**成果物**: `data/lifesim/event_schema.json`（イベント1件の構造定義）＋検証ツール — **設計は🤝、実装/検証は🤖**

> 条件は**コードでなくデータ(宣言的DSL)**で書く。量産との相性・ビルド時全数検証・静的到達性解析のため。

| サブステップ | 内容 | 担当 |
|---|---|---|
| 3-1 | イベント1件のフィールド設計: `id / stage / if(条件) / weight / once / cooldown / text / choices[]` | 🤝 |
| 3-2 | **条件DSLの仕様**: `flags.has / stats.X{gte,lte} / resources.X / relations.X / age範囲 / hidden.X` 等の演算子セット | 🤝 |
| 3-3 | **効果(effects)の仕様**: `stats.X +N / flags.add/remove / resources.X / relations.X / history追記 / 次イベント予約` | 🤝 |
| 3-4 | 選択肢の確率効果（成功/失敗を stats+hidden.luck で判定する仕組み） | 🧑‍🎨判断 → 🤖 |
| 3-5 | **静的検証ツール**: 全イベントの参照を state_schema と突合。未定義フラグ参照・typo・誰もセットしないフラグの参照・誰も参照しないフラグのセットを検出 | 🤖 |
| 3-6 | **到達性解析**: 各イベントを発火できる状態が存在するか（デッドイベント検出） | 🤖 |

**イベントの例（過去の選択がフラグ経由で後に効く）:**
```json
{
  "id": "reunion_band_regret",
  "stage": ["middle_age"], "weight": 2, "once": true,
  "if": { "flags.has": ["quit_club"], "stats.mental": { "lte": 50 } },
  "text": "同窓会で、バンドを続けた同級生がメジャーデビューしていた…",
  "choices": [
    { "text": "心から祝福する",   "effects": { "stats.mental": 10, "relations.best_friend_ken": 15 } },
    { "text": "今からギターを買う", "effects": { "resources.money": -200000, "flags.add": ["hobby.band_restart"] } }
  ]
}
```

**完了条件**: スキーマ確定＋検証ツールが動き、サンプル10件が全数チェックを通る。

| 4-4 | **ランダム率ツマミ**: 状態無視の純ランダムイベントを差し込む頻度（青天の霹靂の制御。サイコロの代替） | 🧑‍🎨数値 → 🤖 |
| 4-5 | **終了条件 & エンディング分岐**: 寿命/早世/特殊エンド。最終評価軸（資産だけでない: 幸福度/達成/人間関係…） | 🧑‍🎨 |
| 4-6 | **マルチ設計**（0-1 で並走型を選んだ場合）: 交差ポイントの仕組み、他人の状態をどう自分のイベントに登場させるか、同期/非同期 | 🧑‍🎨 → 🤖 |
| 4-7 | エッジケース整理: 全員死亡/同時進行のズレ/途中切断/超長寿 | 🤖 |
| 4-8 | **早期モンテカルロ**: 最小イベントセットで数千人生を走らせ、寿命分布・破産率・各ステータスのカーブが意図通りか確認（コンテンツ量産前に骨格を固める） | 🤖 |

## STEP 5.5. 垂直スライス — 骨格の一周 ★統合の検証

**成果物**: **遊べる最小のゲーム**（5〜6シーンで誕生から死まで） — **設計は🤝、実装は🤖、面白さの判定は🧑‍🎨**

### スライスの選び方 — 「短いゲーム」ではなく「全機構を1回ずつ触るゲーム」

5シーンをテーマで選ぶのではなく、**未検証の機構を1つずつ潰せるように**選ぶ。特に**フラグ配線と回収**（このゲームの主題そのもの）は、立てる側と読む側の2シーンが繋がって初めて検証できる。

| # | シーン | 検証する機構 |
|---|---|---|
| 1 | 誕生 | 出生ステータスのランダム生成、`innate`（talent / upbringing）、出生バイアス注入 |
| 2 | 学生期 | **方針選択**(4-1b)、抽選と weight 補正、`register: comic` の演出、**後年に効くフラグを立てる選択** |
| 3 | 成人期 | **2で立てたフラグを読むイベント**＝伏線回収の実証。NPC状態フックが画面に出る |
| 4 | 中年期 | `register: grave`（不可逆な効果）、`crisis_*`、`history` への thread 記録 |
| 5 | 老年期 → 死 → エンディング | 終了条件、**エンディング判定式が8軸のうち最低2つに分岐できること**、人生ダイジェスト |

各ステージ間は**モンタージュで飛ばす**（間を埋めるのはSTEP 6）。`register` は comic / warm / grave の3種すべてを最低1回ずつ使い、演出が切り替わることを確認する。

**設計で詰め切る**（後から変えると高くつく。STEP 2〜5 で確定させる）:

**完了条件**: 誕生から死まで通してプレイでき、2の選択が3で実際に効くことを目で確認でき、エンディングが選択によって分岐する。**ここで「面白い兆しがあるか」を判定し、無ければ量産に入らない。**

**運用上の要点:**

- **下書きはサブエージェントに委譲する。** Claude Code の Task ツールは `model` を個別指定できるので、主ループを Opus 5 に置いたまま下書きだけ Sonnet 5 のサブエージェントに投げられる。モデル切り替えのためにセッションを分ける必要はない
- **バッチで生成する。** 1リクエストで5〜10本。トーンガイドとスキーマの再送コストが本数ぶん薄まる
